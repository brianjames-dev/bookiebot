# Recorded transactions in the app

Transactions combines the Daily Spending chart and Date column/Quiet indent list with the existing recorded-transaction actions. Overview ends after its four-chart carousel; standalone signed reports retain read-only Daily Spending. Ask's activity source opens Transactions.

The single **All** chooser beside Total Spent filters both chart and list by Needs, Wants, Shared or category. Income and cash Savings remain accessible in that chooser, with Total Income / Total Saved labels. All means recorded spending (expenses and bill payments), not income or savings. Search sits below the total and matches descriptions, locations, people/cards, dates and amounts; there are no separate people/card/status filters. The period control offers the selected month or All months across configured existing annual workbooks. This remains separate from Plaid review and excludes scheduled estimates and derived ESPP totals. Shared purchases use the canonical full purchase amount, matching their edit/review rows; this recorded-activity total can differ from Overview's Current/Projected budget total and net amounts after repayments. Scheduled status semantics are not changed by this merger.

Days are newest first. Multi-entry headers keep overlapping 28px merchant circles/category dots, Today, exact totals and native snake expansion. Single-entry days have no extra separator above their text and show the same right-aligned amount once, the same circle/badge and supporting category/item text, without expansion. Expanded entries keep category order, quiet indentation and a count that fades into the parent row. Left swipes reveal joined, equal-width **Update / Split / Delete** buttons according to source capabilities. Only a deliberate horizontal swipe reveals actions for pointer/touch input; taps, micro-movements and vertical scrolling do not. Only one row can be open; full swipes never execute an action. Icons stay opaque and clip immediately at a fixed row edge. Both directions use the same 420ms easing, with a 12px amount/action gap and 8px rail corners. Keyboard users can activate Show actions or use Left / Right / Escape. Controls remain focusable with no visible focus borders, outlines or focus shadows, as requested.

Results load in pages of 40, but chart/day counts and exact-cent totals cover the complete filtered snapshot before pagination. Partial days say how many entries are loaded. A changed snapshot blocks appending shifted/duplicate rows and offers Refresh. Failed reads are errors, not an empty history; pending filters retain the previous chart with its matching labels until a new result arrives. Two batched worksheet reads per annual workbook load existing monthly sources and action logs; owner/month browsing snapshots last 30 seconds. Search and filtering reuse them. Explicit Refresh and financial-change events request fresh source data and replace the browsing cache. Opening the tab is lazy and adds no sheet reads to initial Overview loading.

## Actions and confirmation

Split and Edit split offer **Custom** for current shared allocations. Brian/Hannah each have an editable dollar amount above a calculated, read-only percentage. Enter either dollar amount or move the slider by cents; the other side updates automatically so both amounts equal the full purchase. New custom drafts start at 50/50, while existing custom splits reopen their exact saved amounts. Review shows the same named shares before Confirm split; Back retains the draft and Cancel discards it. Invalid amounts disable Review with a correction hint. Historical legacy splits retain their existing supported methods.

Custom dollar splits save an exact amount ratio in the same canonical allocation used by Shared, preserving every entered cent. Later full-amount corrections scale that saved ratio with half-up cent rounding; existing percentage splits remain compatible. Choosing or confirming a split never marks a repayment received; pending/received/cleared repayment guards remain in force. Saved receipts and lost-response recovery retain the reviewed amounts and both named shares.

Update includes Category when the source permits moving. An unchanged category uses the existing Update command; a category change sends one existing Move command containing all edited fields, including amount and any required destination item. It never chains Update followed by Move. The user sees one Update review/confirmation and a saved Update receipt; category and field changes are explicit in review, receipt and supported Undo. Discord's separate Move controls remain compatible. Split contains the existing split editor and reviewed Remove split action. Dates stay source-controlled. Income supports source/amount edits; fixed bill and savings rows retain their existing amount-only restrictions. Split review shows full purchase amount and both named shares, recalculated when a combined amount/category edit changes a split purchase. Matching a bank record and recording a repayment remain separate.

Every action has a fresh read-only review and an explicit confirmation. The server revalidates owner, selected month, exact saved source, current values, canonical version and normalized changes immediately before calling the existing financial service. Current and historical worksheets are bound to one worker with a context-local repository, rather than changing process-global routing or the clock. Historical splits retain their source workbook year. Existing canonical projection, pending-report, receipt, cleared-balance and correction guards remain authoritative; supported Undo is exposed after success and as a persistent Undo last change shortcut. Undo of a deleted transaction targets its exact saved deletion record. Shared corrections keep the existing audit/repayment reversal rules rather than offering an unsafe general Undo.

Undo of Update compares the current fields/amount with the saved restoration target using **Current → Restore to**. Undo of Move names the original category and shows the current → restored category explicitly. Completed Undo receipts show **Previous → Restored**; saved-status reads and identical-request replay retain that same display evidence. The extra context comes from the existing fresh owner-scoped source snapshot, without an additional sheet read or changes to Undo's writer, source/version checks or confirmation. Older saved responses remain compatible.

Transactions requests use the app's same-origin referrer policy so Safari retains a valid Origin despite the page's no-referrer privacy policy. Cross-origin requests remain blocked; a review never falls back to a financial command. If an older Safari frontend shows Try again immediately after Review change, load the current app update before retrying the review.

Manual sheet expenses, income, bill actuals and cash savings remain visible without creating action logs on browse. Explicit confirmation may adopt the existing row as audit lineage, then apply the chosen action; it does not import or duplicate a financial row. Generated reimbursement/offset rows and linked recipient bill cells are read-only here and point to Shared. Canonical source identity wins over a guessed manual source. Stale saved row references cannot expose a shifted neighbor as the original purchase.

## Recovery and audit

Successful changes show a saved-change receipt with the transaction, changed fields, clear Previous/Updated values and supported Undo. Category changes use the Update heading; Delete, Split and Undo keep their own headings; split amounts remain separate from repayments. The same structured details appear before confirmation. Dismiss hides the completed receipt without changing a transaction; the saved Undo remains discoverable. Discord-formatted audit text is retained internally and never shown as a web success message. Older saved responses without structured details show a concise success fallback.

Two small operational tables in the existing authenticated app database reserve owner-scoped confirmation IDs before a writer can run. They retain the frozen command, fingerprint, timestamp and result. Concurrent/repeated requests replay the saved result; an already claimed running or uncertain request is never re-executed. A failed preflight releases further work through a recorded failed result. A write with an unknown outcome, or failed Undo persistence, requires saved-history inspection instead of a blind retry.

The exact request remains in owner-scoped browser session storage through a lost response/reload. The authenticated list also discovers unfinished claims from another session and the latest supported app Undo. Check saved status is read-only; Retry same confirmation retains the original request and cannot repeat a claimed writer. If a process stops mid-write, the conservative claim may require inspection of the frozen command and sheet/action history. New Undo/adoption records carry `app_request_id` for that audit. No new repayment event, bank transaction or financial mirror is created by opening/reviewing/canceling.

Drafts and in-flight/uncertain changes participate in the app work guard. Account changes remount the controller; access failures clear private content. Successful changes refresh Overview and Shared; confirmations stay frozen across unrelated list refreshes. Search responses are canceled/versioned so an older query cannot replace a newer one.

## Acceptance

Use isolated sheets and an isolated SQLite/PostgreSQL database for every financial action. Check all supported fields, required Move item collection, each split method, split cancellation, Delete, successive Updates, adjacent Moves/Deletes and Undo. Verify source/neighbor coordinates, action lineage, bank reopening and unchanged repayments. Include a prior month/year, duplicate requests, stale/foreign source IDs, quota/read failures, lost responses, restart/another-session recovery, generated repayment rows and pending/received/cleared canonical guards.

On production, inspect Overview and Transactions, search/filter, open a review, then Cancel. Do not alter RJ11 or another real transaction as a test. Also test single-entry days, long days spanning pages, the unified chooser/search and rapid swipe reversals, with keyboard focus producing no visible borders. Native iPhone and real user financial acceptance remain separate from isolated automated tests and deployment health checks; checklist 156 records the release procedure.
