# Recorded transactions in the app

Entered bills now follow their saved withdrawal/autopay date. Future or
unresolved dates keep the amount queued in Calendar/Projected and outside this
recorded workspace. On the withdrawal date the existing source appears once,
dated to that withdrawal, with the same edit/split/Undo identity. Unentered
estimates never become transaction rows. See [Bill payment timing](BILL_PAYMENT_TIMING.md).

Recurring subscriptions join the list on/after their saved withdrawal dates in Pacific time, using the same active subscriptions, amounts, monthly/yearly dates and month-end clamping as Current. Future charges stay in Calendar/Projected; invalid/missing dates, inactive and zero-amount subscriptions do not create rows. For the reported November example, Xfinity ($61.50, November 2) and Slate Digital ($14.99, November 4) close the $76.49 gap between $2,616.58 in Transactions and $2,693.07 in Current.

Each subscription is a schedule-derived, owner/month-scoped occurrence, with stable identity across refreshes and price/date corrections. It has a normal merchant logo or category-colored repeat fallback, plus Subs (Needs)/Subs (Wants) filtering and correctly attributed daily/chart totals. Search and 40-row pagination include these rows. All months uses each existing annual workbook's subscription source. Occurrences have no purchase action-log ID or Update/Move/Split/Delete/Undo capabilities: change the saved subscription schedule instead. Reads neither log another expense nor modify a bank/reimbursement record. Duplicate saved schedule lines remain distinct, matching Current; there is no fuzzy deduplication of separately logged purchases.

Transactions opens with the Date column/Quiet indent list and existing recorded-transaction actions. The circular graph button beside All smoothly reveals or hides the native Daily Spending chart below Total Spent/filter and above search; it starts hidden, retains its chart instance through reversals and makes no data requests. Overview ends after its four-chart carousel; standalone signed reports retain read-only Daily Spending. Ask's activity source opens Transactions.

With **Settings → Appearance → Duo landscape layout** enabled, open landscape uses two physical panes. The native list, period and scope controls stay left with a bounded results scroller; Daily Spending stays right above the existing horizontal dock. Tap a row for its right-side Edit / Split / Delete chooser. The same native editors, review/confirmation, interrupted-save recovery and Undo replace the graph there. The graph button peeks at the chart and returns to the same draft; Cancel/close restores it. Draft/review state, including invalid custom-split text and validation, follows folds. Closed portrait and ordinary devices retain their inline/swipe workflow and graph preference. No financial request, command identity, confirmation or repayment semantics change.

The single **All** chooser beside Total Spent filters both chart and list by Needs, Wants, Shared or category. Income and cash Savings remain accessible in that chooser, with Total Income / Total Saved labels. All means recorded spending (expenses, bill payments and elapsed subscription charges), not income or savings. Search sits below the total and matches descriptions, locations, people/cards, dates and amounts; there are no separate people/card/status filters. The period control offers the selected month or All months across configured existing annual workbooks. This remains separate from Plaid review and excludes scheduled estimates and derived ESPP totals.

Shared bill payments display the original bill minus confirmed repayments received, matching the payer's current cash exposure. For a $200 bill, a confirmed $40 repayment shows $160; an unconfirmed sent-payment report still shows $200. Partial/full receipts and reversals update the row, day total, Total Spent and optional graph together. Resetting debt does not invent a repayment. Canonical confirmed cash remains authoritative while its sheet projection syncs; missing source logs and zero remaining exposure retain the existing bill identity. Recipients' linked bill cells already contain their confirmed share and are not reduced again. Queued withdrawal timing still applies.

The API retains full `amountCents`/`fields.amount` for source editing, split calculations and bank-charge matching, and supplies optional `displayAmountCents` for current-accounting shared bills. Search accepts both displayed and original amounts. Other recorded purchases and historical net-accounting sources keep their existing amount policy; this workspace total can therefore differ from Overview. Received/pending/reset/projection edit guards are unchanged.

Days are newest first. Multi-entry headers keep overlapping 28px merchant circles/category dots, a current-date marker with the actual weekday, exact totals and native snake expansion. Single-entry and collapsed multi-entry day sections share a 72px content height plus their 1px divider, with 8px vertical padding. The nested guide stops 6px above the day divider without adding space below the final purchase. Single-entry days have no extra separator above their text and show the same right-aligned amount once, the same circle/badge and supporting category/item text, without expansion. Expanded entries keep category order, quiet indentation and a count that fades into the parent row. Left swipes reveal joined, equal-width icon-only **Update / Split / Delete** buttons according to source capabilities. Only a deliberate horizontal swipe reveals actions for pointer/touch input; taps, micro-movements and vertical scrolling do not. Only one row can be open; full swipes never execute an action. Icons stay opaque and clip immediately at a fixed row edge. The sage Update, blue Split and red Delete actions share the row’s physical track. Both directions use the same 420ms easing, with no gap between the sliding row and action rail, a retained 10px amount inset and 8px rail corners. Keyboard users can activate Show actions or use Left / Right / Escape. Controls remain focusable with no visible focus borders, outlines or focus shadows, as requested.

Results load in pages of 40, but chart/day counts and exact-cent totals cover the complete filtered snapshot before pagination. Partial days say how many entries are loaded. A changed snapshot blocks appending shifted/duplicate rows and offers Refresh. Failed reads are errors, not an empty history; pending filters retain the previous chart with its matching labels until a new result arrives. Two batched worksheet reads per annual workbook load existing monthly sources and action logs; owner/month browsing snapshots last 30 seconds. Search and filtering reuse them. Explicit Refresh and financial-change events request fresh source data and replace the browsing cache. Opening the tab is lazy and adds no sheet reads to initial Overview loading.

## Actions and confirmation

Actions expand inside their selected row. Only the rounded editor surface receives the subtle 4% sage tint and 4px top/bottom padding; the purchase row and logo/guide gutter retain the page background. Update has compact underlined fields with merchant/card always visible; no repeated title or extra disclosure. Only valid meaningful changes enable Review. Review slides in from the right while height resizes (440ms), uses the same struck old → new styling for every field/category, and has no redundant heading. Back preserves the draft; Cancel or parent-day collapse discards its action/review.

Split uses the approved **Rising fill** circles. Each circle’s filled area tracks the named person’s share. A small **pie icon** restores By income using the server writer’s exact cents; it is enabled away from that allocation and dim/disabled at it. The slider gently catches fronted, equal and income notches, with quarter-dollar increments elsewhere. Manual dollar fields retain exact cents. Current splits reopen their saved allocations; new ones begin at the actual income allocation. Legacy/custom capabilities and fronting eligibility remain enforced, and Remove split retains its reviewed flow.

Custom dollar splits save an exact amount ratio in the same canonical allocation used by Shared, preserving every entered cent. Later full-amount corrections scale that saved ratio with half-up cent rounding; existing percentage splits remain compatible. Choosing or confirming a split never marks a repayment received; pending/received/cleared repayment guards remain in force. Server reviews, saved results and lost-response recovery retain the reviewed amounts and both named shares.

Update includes Category when the source permits moving. An unchanged category uses the existing Update command; a category change sends one existing Move command containing all edited fields, including amount and any required destination item. It never chains Update followed by Move. The user sees one Update review/confirmation and confirmed row feedback; category and field changes are explicit in review and supported Undo. Discord's separate Move controls remain compatible. Split contains the existing split editor and reviewed Remove split action. Dates stay source-controlled. Income supports source/amount edits; fixed bill and savings rows retain their existing amount-only restrictions. Split review shows full purchase amount and both named shares, recalculated when a combined amount/category edit changes a split purchase. Matching a bank record and recording a repayment remain separate.

Every action has a fresh read-only review and an explicit confirmation. The server revalidates owner, selected month, exact saved source, current values, canonical version and normalized changes immediately before calling the existing financial service. Current and historical worksheets are bound to one worker with a context-local repository, rather than changing process-global routing or the clock. Historical splits retain their source workbook year. Existing canonical projection, pending-report, receipt, cleared-balance and correction guards remain authoritative; supported Undo is exposed only in the short-lived popup after confirmed feedback. Undo of a deleted transaction targets its exact saved deletion record. Shared corrections keep the existing audit/repayment reversal rules rather than offering an unsafe general Undo.

The timed Undo button is the explicit Undo instruction. It obtains a fresh server Undo review and submits that exact reviewed confirmation once; deleted entries still target their exact saved deletion record. Expiry or dismissal changes no financial state. Existing restoration context remains in stored results/reviews for audit and compatibility.

Transactions requests use the app's same-origin referrer policy so Safari retains a valid Origin despite the page's no-referrer privacy policy. Cross-origin requests remain blocked; a review never falls back to a financial command. If an older Safari frontend shows Try again immediately after Review change, load the current app update before retrying the review.

Manual sheet expenses, income, bill actuals and cash savings remain visible without creating action logs on browse. Explicit confirmation may adopt the existing row as audit lineage, then apply the chosen action; it does not import or duplicate a financial row. Generated reimbursement/offset rows and linked recipient bill cells are read-only here and point to Shared. Canonical source identity wins over a guessed manual source. Stale saved row references cannot expose a shifted neighbor as the original purchase.

## Recovery and audit

Only a verified successful command starts feedback. The editor closes before changed amounts roll and text pauses, strikes through, rests and fades to its new value. Category reorders lift the real crisp row, make room, travel and settle; unchanged sort positions skip that flight. All motion respects Reduce Motion. The workspace stays inert until a fresh canonical listing succeeds; a failed read offers Refresh without submitting another financial command. A supported Undo popup then appears for eight seconds. There are no persistent receipt panels, preview-restored messages or Undo last change controls. Discord-formatted audit text remains internal.

Two small operational tables in the existing authenticated app database reserve owner-scoped confirmation IDs before a writer can run. They retain the frozen command, fingerprint, timestamp and result. Concurrent/repeated requests replay the saved result; an already claimed running or uncertain request is never re-executed. A failed preflight releases further work through a recorded failed result. A write with an unknown outcome, or failed Undo persistence, requires saved-history inspection instead of a blind retry.

The exact request remains in owner-scoped browser session storage through a lost response/reload. The authenticated list also discovers unfinished claims from another session and any supported saved Undo metadata for compatibility; the normal UI exposes Undo only during its popup. Check saved status is read-only; Retry same confirmation retains the original request and cannot repeat a claimed writer. If a process stops mid-write, the conservative claim may require inspection of the frozen command and sheet/action history. New Undo/adoption records carry `app_request_id` for that audit. No new repayment event, bank transaction or financial mirror is created by opening/reviewing/canceling.

Drafts and in-flight/uncertain changes participate in the app work guard. Account changes remount the controller; access failures clear private content. Successful changes refresh Overview and Shared; confirmations stay frozen across unrelated list refreshes. Search responses are canceled/versioned so an older query cannot replace a newer one.

## Acceptance

Use isolated sheets and an isolated SQLite/PostgreSQL database for every financial action. Check all supported fields, required Move item collection, each split method, split cancellation, Delete, successive Updates, adjacent Moves/Deletes and Undo. Verify source/neighbor coordinates, action lineage, bank reopening and unchanged repayments. Include a prior month/year, duplicate requests, stale/foreign source IDs, quota/read failures, lost responses, restart/another-session recovery, generated repayment rows and pending/received/cleared canonical guards.

On production, inspect Overview and Transactions, search/filter, open a review, then Cancel. Do not alter RJ11 or another real transaction as a test. Also test single-entry days, long days spanning pages, the unified chooser/search and rapid swipe reversals, with keyboard focus producing no visible borders. Native iPhone and real user financial acceptance remain separate from isolated automated tests and deployment health checks; checklist 156 records the release procedure.
